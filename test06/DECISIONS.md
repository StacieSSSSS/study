# DECISIONS.md

记录项目中具有架构影响的决策，包括分层调整、依赖引入/替换、数据模型变更、对外契约变更等。日常的小修复、重命名、注释等不需要记录。

每个决策按下方模板新增一条，追加在文件末尾（不要修改历史条目，如需变更已有决策，新增一条并在“关联”中引用被替代的条目）。

## 模板

```
## D{编号} - {决策标题}

- 日期: YYYY-MM-DD
- 状态: 提议 / 已采纳 / 已废弃 / 已替代
- 背景: 为什么需要做这个决策，遇到了什么问题或约束
- 决策: 最终选择的方案
- 备选方案: 列出考虑过但未采用的方案及未采用原因
- 影响: 对架构 / 性能 / 测试 / 后续开发的影响
- 关联: 关联的 issue / PR / 其他 D{编号}
```

## D001 - 采用三层架构（api / services / repositories）

- 日期: 2026-06-20
- 状态: 已采纳
- 背景: 项目初始化阶段需要确定代码分层方式，避免路由层直接耦合数据库访问，导致业务逻辑分散、难以测试和维护。
- 决策: 采用 `api/`（路由与协议转换）→ `services/`（业务逻辑）→ `repositories/`（数据访问）三层架构，单向依赖，路由层禁止直接查询数据库。
- 备选方案:
  - 单文件/双层架构（路由层直接调用数据库）：开发初期更快，但业务逻辑会散落在路由函数中，难以单独测试和复用，随项目增长维护成本会快速上升，未采用。
  - 四层架构（增加单独的 DTO/Schema 层）：当前项目规模较小，FastAPI 自带的 Pydantic 模型已可承担协议转换职责，暂不需要额外分层，未采用。
- 影响: 所有新代码必须明确归类到对应层；测试目录结构需镜像三层结构；CLAUDE.md 中的 Constraints 与 Self-Check 章节据此约束代码评审标准。
- 关联: 见 `CLAUDE.md` 中 Architecture / Constraints 章节。

## D002 - 使用 SQLite 作为初始数据存储

- 日期: 2026-06-20
- 状态: 已采纳
- 背景: 项目初期需要一个零运维成本、易于本地开发和测试的数据存储方案。
- 决策: 使用 SQLite 作为当前阶段的数据库，所有访问通过 `repositories/` 层封装。
- 备选方案:
  - PostgreSQL：功能更完善，但需要额外的运维与本地环境配置，初期不需要，未采用。
- 影响: 数据访问层的接口设计需保持与具体数据库无关（便于未来迁移到其他数据库时只需替换 `repositories/` 实现）。
- 关联: 无
